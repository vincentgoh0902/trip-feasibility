# Annotation guide

How to build the evaluation dataset: 40 itineraries generated by ChatGPT, Claude and Gemini,
each annotated with what's really wrong with it. Every reported number in this project
is measured against these annotations, so they need to be right and independent of the
checker.

Files you'll use:

| File | What it is |
|---|---|
| `docs/annotation/template.yaml` | Blank itinerary file to copy |
| `docs/annotation/example.yaml`, `example.md` | A fully annotated, made-up example and its text (not in the dataset) |
| `data/dataset/hotels.yaml` | The 16 hotels, for you to label |
| `data/dataset/itineraries/<id>.yaml` | One file per itinerary: metadata and labels (you create these) |
| `data/dataset/texts/<id>.md` | Its text: the chatbot reply exactly as copied (`scripts/save_reply.sh`) |
| `docs/TEST_CITIES.md` | Which hotels, and why |

`data/` is gitignored: the dataset never goes to the public repo. Back it up (see the end).

## The workflow

1. **Collect** all 40 itineraries (text and metadata only). About 5 minutes each.
2. **Assign splits** (dev or test) at random.
3. **Label the 16 hotels** in hotels.yaml. About 10 minutes each.
4. **Annotate** each itinerary: its violations (the gold), drafted by GPT or Gemini and
   checked by you, or written by hand. Dev files also have stops and legs, for parser
   debugging only.
5. **Validate** as you go: `uv run python scripts/validate_dataset.py --partial` (from
   `backend/`). Without `--partial` once everything is done.

Collect everything before annotating anything, so the itineraries aren't shaped by what you
learn while annotating.

## 1. Collecting

### The mix

10 itineraries per city (Paris, London, Barcelona, Vienna), 40 in all:

- **Models:** spread each city across ChatGPT, Claude and Gemini (4/3/3, rotating which
  gets 4). Note the model name the app shows.
- **Hotels:** each of the city's 4 hotels (docs/TEST_CITIES.md) in 2–3 itineraries. Use the
  real name with accents ("Hôtel Regina").
- **Length:** 2–4 days. Longer itineraries take much longer to annotate.
- **Dates:** each trip starts on a real date in the next 12 months. In every city, make sure
  some trips include:
  - a public holiday (Christmas to New Year, Easter week, May Day, a national day such as
    14 July in France or 11 September in Catalonia, a London bank holiday);
  - the weekdays museums close: many close on Mondays, the Louvre on Tuesdays.

  Check holiday dates on official government sites, not on this project.
- **Preferences:** most trips can use the defaults (moderate pace, 10 km walking, walk +
  transit). Vary a few: some relaxed, some packed, one or two with a low walking limit, one
  with car or bike.
- **Detail:** about two thirds asking for exact times, a third leaving it loose ("morning:
  ..."). Both kinds occur in real use.

### The prompt

Write it the way a traveller would, and vary the wording. For example:

> Plan a 3-day trip to Barcelona starting Saturday 24 April 2027. I'm staying at Hotel Casa
> Camper. I love architecture and food, and I want to see as much as possible. Give me a
> day-by-day schedule with times. Keep it under 600 words.

- Always name the hotel and the start date (weekday plus date).
- Some prompts can push for a full schedule ("as much as possible") and some for a relaxed
  one. Don't ask for mistakes: the point is to find the ones models make on their own.
- "Under 600 words" keeps the text well within the limit (15,000 characters once cleaned).
- Use a fresh chat for each itinerary (no memory of earlier ones). Don't put personal
  details in the prompt: the itineraries may appear in the public README as examples.

### Saving it

The id is the city plus two digits, `paris-01` to `paris-10` (so "P03" is `paris-03`).

1. **Save the raw reply.** Copy the whole answer (the chatbot's copy button is easiest), then
   from `backend/`:

   ```sh
   scripts/save_reply.sh paris-03          # writes data/dataset/texts/paris-03.md
   ```

   It saves the clipboard exactly and refuses to overwrite an existing reply (`-f` to replace
   it). Keep everything the copy brings along: image links, source citations, map or
   checklist text. That debris is what real users paste, and the checker strips it in code
   before extraction (parse step 0, `parse/clean.py`). This file is the record of exactly what
   the model said.

   Limits: 50,000 characters as copied, 15,000 once cleaned. The validator checks both. Over
   either, regenerate with a shorter word limit rather than cutting the reply. To see the
   cleaned text and its length:

   ```sh
   uv run python scripts/show_clean.py paris-03
   ```

   **Interactive replies** (day tabs, carousels, timeline widgets) don't copy: only the
   surrounding text, or the visible tab, reaches the clipboard. Don't transcribe the widget
   by hand. Regenerate in a fresh chat with the same prompt plus one closing line, *"Reply in
   plain text only, with no interactive widgets or tabs."*, and record that exact prompt in
   `prompt`. Regenerate only for the format, never to get a reply with more or fewer
   mistakes. Before saving, check that every day is in the clipboard (`pbpaste | less`).

2. **Create the itinerary file.** Copy `docs/annotation/template.yaml` to
   `data/dataset/itineraries/<id>.yaml` (the file name must match the id) and fill in:

- The reply doesn't go in this file: it's `texts/<id>.md` from step 1, and the validator
  reads it from there. Don't edit that file; to replace a reply, save it again with `-f`.
- `prompt`, `model`, `source`, `trip_start` (the date of day 1), `preferences` if not default.
- Leave out `stops`, `legs` and `violations` for now.

## 2. Assigning splits

Vienna is held out entirely: all 10 Vienna files get `split: test`.

For each of Paris, London and Barcelona, pick 5 numbers at random for dev:

```sh
python3 -c "import random; print(sorted(random.sample(range(1, 11), 5)))"
```

Those files get `split: dev`; the other 5 get `split: test`. Random choice stops the split
from favouring easier or more interesting itineraries. Don't swap files afterwards.

## 3. Labelling the hotels

For each hotel in `data/dataset/hotels.yaml`, read a fixed sample of its negative reviews:

```sh
uv run python scripts/sample_reviews.py "Hotel Cavendish" -n 40   # use csv_name
```

Then set `red_flags` to the themes that are real red flags, or `[]` if none:

- Themes: `noise`, `cleanliness`, `safety`, `location`.
- A theme is a red flag when several different reviewers complain about the same thing and
  a traveller would want a warning before booking. Rule of thumb, out of the 40 reviews:
  | Theme | Red flag at about |
  | --- | --- |
  | `noise`, `cleanliness` | 4 or more |
  | `location` | 3 or more |
  | `safety` (theft, feeling unsafe, strangers getting in) | 2 or more |

  Rarer themes count at fewer reviews because they come up far less often: a typical hotel's
  complaints are ~8% about noise but ~0.3% about safety, and two theft reports are already
  unusual.
- One-off complaints, things a hotel can't help (street works in 2016), and taste ("decor
  tired") don't count.
- Add a `note` with the counts, e.g. `noise 7/40 (street-facing rooms), cleanliness 5/40`.
- The same seed always shows the same reviews, so a label can be re-checked later.

Judge from the reviews, not from the score or from whether it's on the "low" list.

## 4. Annotating an itinerary

**Violations first (decided 2026-10-27, ARCHITECTURE decision 74).** The gold is the list of
violations, in the itinerary's own words (see Violations below), plus `unknowns` and
`other_issues`. A file counts as annotated, and goes into evals, once it has `violations`
(`[]` when there are none) and `verified_by_human: true`. Write `violations: []` only once
you've checked: it means "checked, none found". See `docs/annotation/example.yaml`.

- **Drafts** may come from an LLM, but never from Anthropic (Claude is the extractor, and a
  draft from the same provider would reward shared blind spots). `drafted_by` records the
  model ID, or `human`. A draft counts only after you've checked every label against reality
  and set `verified_by_human: true`; fix, add or delete labels freely before that.
- **Drafting:** `uv run python scripts/draft_gold.py` (from `backend/`) drafts every dev
  file with no gold yet, using GPT through the Codex CLI with web search. Check each label
  against the official source (fix, add or delete freely), then set
  `verified_by_human: true`. Entries the drafter couldn't quote exactly are named in
  `notes`.
- **`hotel`:** the hotel the prompt names, as its key in hotels.yaml (leave it out if none).
  Its red flags become the hotel labels, so you don't write those.
- `notes` is text, not a list: leave it out when there's nothing to say, never `[]`.
- **Preferences** (if not default) are set before annotating, from the prompt alone, never
  from the reply: "as much as possible" → `packed`, "relaxed" or "not rushed" → `relaxed`,
  kids or limited walking → a lower `max_walk_km`, a rental car → `car`. Set them for all 40
  in one go, and give the dev split some of the variety (at least one relaxed, one packed,
  one low walking limit), since limits are tuned on dev. Don't look at the checker's pace
  limits (`checks/daily_load.py`) first.
- **YAML:** block style (one field per line, as in the example) or inline `{ ... }` both
  work. Always quote times (`"09:00"`). Quote any value containing a comma in inline style,
  and any value containing `: ` or ` #` in either style.

> **Stops and legs below are frozen: dev only, for parser debugging.** No new stop rules
> are added (decision 74); test files get no stops. Gold stops measure extraction (parse
> accuracy, gold-stop mode); no label depends on them. Legs no longer produce travel-time
> labels and the validator no longer asks for them: where the text below says a leg is
> required or a label is derived, that's how it worked before decision 74.

### Stops (dev only, for parser debugging; frozen)

The stops are what a careful reader would extract from the text, in the order written:

| Field | Rule |
|---|---|
| `id` | `s1`, `s2`, ... in order |
| `day` | Day number as in the text (1 = `trip_start`) |
| `start_time`, `end_time` | Only if the text states them. Otherwise leave them out; never guess. "9:00–12:00" → `"09:00"`, `"12:00"` (quoted) |
| `time_of_day` | Only when the text says morning, afternoon or evening instead of times (see below) |
| `duration_min`, `duration_max` | Only if the text states how long to spend there, in minutes: "allow 30–40 minutes" → `30`, `40`; "about 2 hours" → `120`, `120`; "1.5–2h" → `90`, `120`; "at least an hour" → `60` and no `duration_max`. Otherwise leave both out. Works alongside a time or `time_of_day` |
| `travel_start`, `travel_min`, `travel_max` | The journey *to* this stop, only as the text states it: the stated departure ("9:15 Travel to the Old Harbour" → `"09:15"`) and how long it says the journey takes ("allow 30–40 minutes" → `30`, `40`). Each only when stated. They go on the stop being travelled to; the travel section itself is never a stop. A claim to check, not a leg: your leg is still looked up |
| `place_name` | Copied **exactly** as written, e.g. `Louvre Museum`, even if misspelled. Copy it from the cleaned text (`scripts/show_clean.py <id>`), which is what extraction sees: it differs from the raw reply only where an escape or entity was decoded (`\&` → `&`) or a link reduced to its text. The validator checks it appears in the cleaned text. When a heading wraps the name in other words ("Old Harbour photo stop", "Morning at the City Museum"), copy only the name (`Old Harbour`, `City Museum`) |
| `type` | `venue` (sights, museums, shops, shows, timed activities), `meal` (a named restaurant, café or market eaten at, or a timed meal slot), `hotel`, `transfer` (stations, airports, journeys) |
| `located` | Write `located: false` when `place_name` is the activity's own words rather than a place (`Lunch`, `Breakfast`, `Lunch break`: a timed slot that names none). Leave it out otherwise, areas included (`Champ de Mars` can be found, roughly) |
| `hotel` | Hotel stops only: the key from hotels.yaml, e.g. `paris-regina` |
| `osm` | Optional; leave it out for now |

Vague times:

- Several places under one "Morning:" heading each get `time_of_day: morning`, in text order.
- Stated times win: "Morning (9:00–11:00)" → `start_time`/`end_time`, no `time_of_day`.
- A duration isn't an end time: "09:15, allow 30–40 min" → `start_time: "09:15"`,
  `duration_min: 30`, `duration_max: 40`, no `end_time`. Never compute an end from a duration
  (it can still inform your `daily_load` judgement). It does count for which legs to record
  (see Legs); travel-time labels still need a stated end.
- Clear synonyms only: "late morning" → morning; "night", "after dinner" → evening.
- Anything else ("lunch", "midday", "sunset", "then"): no times and no `time_of_day`.
  Never guess; mention it in `notes` if it matters.

What counts as a stop: a place the traveller goes to. Not stops: general advice ("buy a
Navigo pass"), alternatives ("or, if it rains, ..."), a choice the text leaves open ("the art
museum or the history museum": neither is a stop; say so in `notes`), untimed meals and
activities with no named place ("lunch nearby", "a boat trip on the river"; a named operator
or venue is a stop), entrance tips ("use the side entrance"), prices, and the route between two stops
("a 20-minute walk along the river"). A travel section is a route too, even under its own
heading ("Travel to the Old Harbour: allow 30–40 minutes by public transport"): no stop, and
its time isn't a `duration_*` of the stops either side. What it states goes in the next
stop's `travel_*` fields; the place comes from the section where the visit is, and the
journey's real time goes in a leg, looked up as usual, never taken from the itinerary. Advice on how to get there ("a taxi is easier")
doesn't change `preferences`. A park or garden on the way becomes a stop only when
the schedule gives it its own slot. For a meal described as an area ("lunch in Le Marais"),
use the area as `place_name`; it won't get an opening-hours label.

**A timed slot is a stop**, even with no named place: a meal or activity the schedule gives
its own stated time or duration ("12:45 Lunch near the cathedral: pick a café around Market
Square, budget 60 minutes") takes time out of the day, and leaving it out would make the
gaps around it look like travel slack. For `place_name`, copy the most specific area words
the text gives (`Market Square`), preferring an area over a landmark it's only near (the
cathedral would read as a visit to the cathedral); with no place words at all, copy the
activity's own words (`Lunch break`). Type `meal` or `venue` as usual, times and durations as
stated, and no `opening_hours` label unless a specific venue is named. A timed slot that
leaves the place open ("8:30 Breakfast at the hotel or a café near the station") is a stop
too, named by the activity's own words (`Breakfast`): the time counts even though the place
can't be located. Untimed choices stay non-stops.

More cases (decided 2026-10-26):

- **Downtime** with no place ("Early night", "Back to the hotel to rest", "Free time", "Easy
  evening", "Rest or explore the Eixample") isn't a stop: slack by design. A return to a
  *named* hotel ("Return to Batty Langley's") is a hotel stop.
- **Arrivals and departures** ("Arrive, drop bags at the hotel", "head to the airport") aren't
  stops unless a station, airport or hotel is named.
- **A timed line that is a journey** ("12:00 Taxi up to MNAC", "08:00 RER C (about 40
  minutes)", "Travel to Covent Garden") puts its time in the next stop's `travel_start` (and
  `travel_min`/`travel_max` if a length is stated), not its `start_time`. A day-trip train is
  the same: travel fields, not a `transfer` stop.
- **Several places in one timed slot** ("14:00 Walk to the Panthéon and the Luxembourg
  Gardens"): each named place is a stop; the first takes the slot's start, the last its end,
  any in between no time. Never give each the whole range (that would invent overlaps). Places
  only passed ("past the Globe") are route.
- **Places inside an area visit** ("Gothic Quarter, stopping by the Cathedral and Plaça del
  Rei") are separate stops too, as above. Rooms or features of one venue (the Hall of Mirrors
  in the château, a lake in the park) aren't.
- **A timed choice with a favourite** ("Tate Modern or The London Eye" where the text describes
  the Tate and calls the Eye an alternative; "the Orangerie, or skip it for more Louvre"): the
  favoured option is the stop. Equal options use the activity's words (a timed slot, above).
- **"Morning:", "Afternoon:", "Evening:"** count as a timed slot.
- **"Optional"** items aren't stops, even timed: the plan stands without them.
- **An obvious typo in a time** ("9:30 AM – 11:30 PM" for a morning visit) is kept as written,
  with a note.
- **A slot that carries on at the place just named** ("6:00 Head to Sky Garden", then "6:30–7:30
  Drinks with a view") takes that place's name (`Sky Garden`).

A booking checklist, summary or recap at the end that names places already in the schedule
adds no stops: each visit is one stop, from the schedule. Places only recommended outside the
day-by-day schedule ("Where to eat: Cal Pep, Bar Mut", "If you have more time: Park Güell")
aren't stops either, even when named: a stop belongs to a day because the schedule puts it
there. A place the schedule names inside a day ("lunch at one of the tapas bars below")
points to the list without picking one, so it's a meal with no place: a stop only if it has
its own time or duration (a timed slot, above).

Keep stops in the order of the text; if the text's own order is impossible (an afternoon
stop listed before a morning one), keep the text's order and mention it in `notes`.

### Legs: real travel times (dev only, for parser debugging; frozen)

Record a leg for **every pair of consecutive stops on the same day with less than 60
minutes between them** (the end of one and the start of the next, both stated). A stop with
a start time and a duration but no stated end counts as ending at start + `duration_max` (or
`duration_min` when there's no max): "10:00, allow 30–40 min" then "10:45" is 5 minutes
apart, so record that leg too (also when the sum overlaps the next start). The validator
lists any you miss. Add others too when you suspect the journey takes longer than
the gap (a day trip to Versailles, say).

- Look the journey up in Google Maps or Citymapper, departing at the first stop's end time,
  on the trip's actual weekday (same season if the exact date isn't available yet).
- Use the fastest option within the itinerary's `preferences.transport_modes` (by default
  walk or public transport). Door to door, including walking to and from stations.
- `minutes`: the total, as a whole number. `mode`: what that option mostly is (`walk`,
  `transit`, `bike`, `car`). `source`: e.g. `Google Maps`.
- Two stops at the same place (lunch inside a museum) get `minutes: 0`.
- A stop with only `time_of_day` (or no time) has no stated end or start, so a leg next to it
  is never required, even when the other stop has times ("morning" then "12:15"), and no
  travel-time label comes from it: labels need a stated gap. A day that can't fit is a
  `daily_load` judgement instead.
- A stop with `travel_min` needs a leg from the stop before it (same day), whatever the gap:
  the itinerary's own journey time is checked against yours. If the real time is more than
  10 minutes over `travel_max` (or `travel_min`), that's a derived travel-time warning.
- A stated departure (`travel_start`) counts as the start of the gap instead of the previous
  stop's end: "12:05 head to lunch", lunch at 12:15, is a 10-minute gap.
- No leg to or from a stop with `located: false`: there's nowhere to look up, so the
  validator never asks for one (and refuses one). Its time still counts for `daily_load`.
- A gap counted from a duration only decides which legs to record. Travel-time labels still
  come only from stated ends, until the check itself uses durations.

Legs no longer produce labels: travel-time problems are labelled directly (Violations).

### Violations

One entry per problem, with:

| Field | Rule |
|---|---|
| `check` | `opening_hours`, `public_holidays`, `travel_time` or `daily_load` |
| `day` | Day number as in the text (1 = `trip_start`) |
| `place` | opening_hours and travel_time only: the place **copied exactly** from the cleaned text (`scripts/show_clean.py <id>`); travel_time names the place travelled *to* |
| `from_place` | travel_time only, optional: the place left, copied the same way |
| `time` | Optional: the time as written ("9:30 AM – 11:00 AM"), copied exactly |
| `severity` | `blocker`: doesn't work as written. `warning`: works, but risky or partly wrong |
| `evidence` | One sentence: what's wrong and the fact that shows it |
| `source` | Where the fact comes from: the official page (URL), "Google Maps", or "judgement" |
| `confidence` | `verified`: you looked it up for that date. `estimated`: a judgement (pace, a time you couldn't pin down) |

The validator checks that `place`, `from_place` and `time` appear in the cleaned text. Label
each problem once.

**`unknowns`**: something one of the checks would judge that you couldn't establish (no hours
published, an evening with no time): `check`, `day` and `place` where they apply, and a
`reason`. A prediction matching one isn't counted either way.

**`other_issues`**: real problems outside these checks (a ticket that sells out weeks ahead,
a place in the wrong city), one line each. Not scored.

#### `opening_hours` (names a day and place)

Is the place open for the planned visit, on that date? Use the official website (or Google
Maps if there isn't one), with that date's hours: weekly closing days, seasonal hours,
holiday closures and last admission.

- **blocker**: closed for the whole visit; closed all day (for a visit with no time);
  arriving after last admission; permanently closed.
- **warning**: open for only part of the visit (closes halfway through, opens late).
- Visits with only morning/afternoon/evening are judged on the standard windows: morning
  09:00–12:00, afternoon 13:00–17:00, evening 18:00–21:00.
- Only venues and named meals. No labels for hotels, stations, parks and squares that are
  always open; places you can't establish hours for go in `unknowns`.

#### `public_holidays` (names a day)

Is the day a public holiday in that city, and does it have at least one venue visit?

- National holidays, plus regional ones that apply in the city (Catalonia for Barcelona,
  the state of Vienna, England for London).
- Always a **warning**: closures and crowds are likely. If a venue is actually closed for
  the holiday, label that separately as `opening_hours`.
- Use the official government holiday list.

#### `travel_time` (names a day and the place travelled to)

Can the traveller get from one place to the next in the time the plan leaves? Look the
journey up door to door in Google Maps or Citymapper, departing when the first visit ends,
on the trip's weekday, with the fastest option within `preferences.transport_modes`. Put
the real time and the gap in `evidence` ("12:00 to 12:10, but the metro takes 25 min").

- **blocker**: the gap is shorter than the journey, or the two visits overlap.
- **warning**: less than 10 minutes to spare; or the itinerary states the journey's length
  and the real one is more than 10 minutes longer.
- Only where the text states both times (an end, or a start + stated duration, and the next
  start) or states the journey. Otherwise there's no gap to judge: a day that can't fit is
  `daily_load`.

#### `daily_load` (names a day)

Is the day too much for this traveller, given their `preferences` (pace, walking limit)?
Judge it as a traveller would. Don't count against a formula.

- **warning**: more than this pace allows comfortably: too many sights, too long a day, or
  more walking than the limit.
- **blocker**: can't realistically be done: the activities need more hours than the day
  has, or the walking is far over the limit.
- Walking distance: roughly add up the walking legs (Google Maps shows distances).
- Usually `confidence: estimated`.

#### Not labelled in the file

- `hotel_red_flags`: worked out from hotels.yaml for the itinerary's `hotel`.
- Minor notes (info level): not part of the evaluation.

## Rules that keep the dataset honest

1. **Truth is the real world**, not this project's data. Don't run the checker, and don't
   look up OpenStreetMap opening hours or Nager.Date to decide a label. Otherwise the
   evaluation only measures whether the checker agrees with its own sources.
2. **Drafts only from another provider than the extractor** (GPT or Gemini, never Claude),
   and never shown our checker's output. Every label is checked by you before
   `verified_by_human: true`; the labels you keep are yours.
3. **Don't edit the generated text.** Mistakes in it are the point.
4. **When unsure, don't label**, and explain in `notes`.
5. **Vienna:** annotate it like the others. The held-out rule is about the checker's results,
   which you won't see until the final test run.
6. **Finished means finished.** After the first evaluation run, don't change labels to
   match the checker. If a label was genuinely wrong, fix it and say so in `notes`; the
   dataset version changes automatically.

## Validating and backing up

From `backend/`:

```sh
uv run python scripts/validate_dataset.py --partial
```

It prints counts per split and city, how many are annotated, the label counts, and a
version hash; then every problem, with the file name. Run it after every few files.

To put every file in the standard layout (gold first, block-style violations and stops,
one-line legs, quoted times, fixed key order):

```sh
uv run python scripts/format_dataset.py           # lists the files that would change
uv run python scripts/format_dataset.py --write   # rewrites them, after a backup copy
```

It changes layout only, never data, and skips files with comments of their own (it would drop
them). The dataset version is a hash of the files, so format before an eval run, not after.

Every itinerary file needs its text in `texts/<id>.md`, with or without `--partial`. Once
everything is collected, run it without `--partial`: a text with no itinerary file is then
an error too.

`data/dataset/` exists only on your Mac, texts included. Copy it somewhere safe
regularly (an external drive, cloud storage, or a separate **private** GitHub repo). Never put
them in the public repo.
